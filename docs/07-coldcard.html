这次失败，恰恰来自那个冲突的缺席

Coldcard · 2021-03 → 2026-07 · 本课最难也最值钱

大白话

史上最大的硬件钱包损失，不是因为设备被攻破。设备好得很。

Coldcard 是最偏执的那一类比特币签名器：只做比特币、air-gap、安全元件、可复现构建。
它芯片里那个真随机数发生器一直是好的。
代码打算做的事情也完全正确：读硬件随机数，再和一个软件生成器混合 —— 标准加固做法。

但那个「读硬件随机数」的调用，在链接的时候接错了地方。

它接到了 MicroPython 里一个「给没有硬件随机数的单片机用的」软件生成器上。

于是：本来要把物理噪声和软件生成器混在一起的操作，
变成了把两个软件生成器混在一起。而这等于什么都没混。

门 2（设备）是好的。门 1（造钥匙）塌了。
而只有门 1 的失败是静默的，所以它塌了五年多没人发现。

往下一层

精确的位置

  1. Coinkite 自家的密码库里写的是 extern uint32_t rng_get(void); —— 声明有这么个函数，但不说它在哪。由链接器去找一个叫 rng_get 的全局符号。
  2. Coldcard 板子自己的代码确实读硬件寄存器。但那个读取函数被声明成了 static —— 对别的编译单元不可见，所以它没有导出 rng_get 这个符号。
  3. MicroPython 导出了一个全局 rng_get。它的实现是一个软件 PRNG， 注释里写得明明白白：这是给「没有 RNG 的 MCU」准备的。
  4. 链接器于是绑到了它。
链接器在这里并不是在两个候选里挑了一个，这里只有一个候选。 要是 Coinkite 导出了自己的 rng_get，就会有两个同名全局定义，构建会直接报 duplicate symbol 失败。这次失败，恰恰来自那个冲突的缺席。 —— Wizardsardine

这一课可以真的跑

课程里有一个最小的 C 工程 + Makefile，用你自己机器上的编译器把这个失效原理完整复现：

  • make broken —— 复现那个构建。链接成功，没有警告。跑三次，三次种子一模一样。
  • make duplicate —— 把 static 去掉。 构建直接因 duplicate symbol 失败。这就是本课的全部。
  • make archive —— 一个更阴的变体：同样两个定义，打包成 .a 之后 链接器不报错了，先出现的赢。你的钱包是否安全取决于构建脚本里两个库的先后顺序。
  • make fixed —— Coinkite 的真实修复，全部发生在构建期。
  • make verify —— 那个 nm 校验脚本。验证路径，不要验证分布。

种子里有什么

那个软件 PRNG 的种子只有两个输入，而且是 XOR 进同一个 32 位字里的（所以不叠加）：

  • 芯片唯一标识符的 32 位 —— 这些位编码的是晶片在晶圆上的坐标。 这个值既不变，也不保密。
  • SysTick —— 一个每毫秒回绕一次的计数器。

Mk2/Mk3 上另一个本该贡献 24.4 位的 RTC 价值为零 —— 它指向一个固件从来没启动过的振荡器。

枚举结果：Mk3 上 4,456,448 个起始状态 = 2²².⁰⁹。 单张 RTX 4090 跑 3 秒。

最该读的一条对比

Mk4/Mk5/Q 约 2⁵²，约 95 年。3 秒 vs 95 年不是「程度」的差别，是「种类」的差别。 这 29.5 位的差距完全来自安全元件那 32 位的 reseed —— Wizardsardine 的原话：它是这整条链里唯一一个真正起了作用的机制。

所以门 2 不是没用。门 2 是在门 1 塌了之后，唯一还在承重的东西。

骰子为什么救了人

在这次事故里，唯一完全没有风险的用户，是那些不相信设备随机数、自己掷了骰子的人。 在纯骰子路径上，哈希累加器从空字符串开始，只吃掷骰结果 —— 设备的熵根本没进来。

Coinkite 的官方阈值：50–98 次独立私密公平的掷骰 → 骰子单独贡献至少 128 位； 99 次以上 → 约 256 位；少于 50 次或者记不清 → 必须迁移。

但混合模式有两个坑：那个「拒绝某一面占比超过 30%」的分布检查只在某个参数为真时才生效； 而从词表界面进入的混合模式同时关掉了那个检查和最少次数要求。

→ 「我掷了骰子」这句话本身不够，得知道是从哪个入口掷的。

cd lessons/07_coldcard_link && make all
